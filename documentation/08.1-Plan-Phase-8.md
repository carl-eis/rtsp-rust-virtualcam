## 1. Where the frame path stands today

From decode to the camera, everything is CPU memory, and everything after the decoder is
portable code shared by Windows, Linux and macOS:

| Stage | Where | What it does | Runs |
|---|---|---|---|
| Decode | `rtspcam-platform/src/windows/mf_decoder.rs` (Windows), `rtspcam-pipeline/src/decode/openh264.rs` (all) | MF decoder MFT found with `MFTEnumEx(SYNCMFT \| LOCALMFT \| SORTANDFILTER)`, no D3D manager set, so **decoding is software** today. Output copied into a `Frame` (`ConvertToContiguousBuffer` + `Lock`) | once per stream |
| `Frame` | `rtspcam-pipeline/src/frame.rs` | Tightly packed NV12 in a `Vec<u8>`, full source resolution, a new allocation per picture | — |
| Crop / rotate / flip, overlay | `rtspcam-engine/src/manager.rs` (`Adjusted::adjust`), `rtspcam-pipeline/src/transform.rs`, `ab_glyph` overlay | Only when the camera's `picture` options change frames; result cached per frame | once per frame |
| Scale + pixel format | `rtspcam-engine/src/source.rs` (`next_frame`), `rtspcam-pipeline/src/scale.rs` | Bilinear fixed-point scaler (scalar code, with a plain row copy when the size doesn't change), then NV12 → BGRA / YUYV / I420. One `Scaler` per camera behind one `Mutex` | **once per consumer per frame** |
| Deliver | Windows: named pipe → `rtspcam_vcam.dll` in Frame Server. Linux (phase L, done): `Pusher` → v4l2loopback device. macOS (phase M): `Pusher` → extension | Bytes over `FrameSource::next_frame(.., out: &mut Vec<u8>)` | per consumer |
| Preview | `rtspcam-app/src/ui/preview.rs` | Its own scale + NV12 → RGBA for Slint | while the window shows it |

The Windows decoder's name, shown in the stream details and logs, is built from the MFT's
friendly name: `Media Foundation (Microsoft H264 Video Decoder MFT)`.

Measured so far ([03 §4.2](03-progress-phases-2-3.md#42-phase-2-exit-criteria)): four
streams (720p/1080p, H.264/H.265) at 30 fps, receive-to-decode 2–3 ms (MF H.264), ~9 ms
(OpenH264), ~14 ms (H.265). **CPU per stage was never measured.** We don't know whether
decode, transform/overlay, scaling or the pipe copy costs the most.

## 2. What we learned, and how it changes the plan

1. **The CPU-bytes contract is shared by every OS.** `Frame`, `FrameBus`, `FrameSource`, the
   `Pusher` and the preview all expect NV12 bytes in memory. GPU textures all the way into the
   camera ("DXGI samples into the virtual camera") would need a GPU variant in each of these
   types, and in the pipe protocol. v4l2loopback (Linux) only takes bytes anyway.
2. **OS code may only live in `rtspcam-platform`** ([09 §3](09-cross-platform-plan.md#where-cfg-may-appear),
   checked in CI). D3D11 code goes in `platform/src/windows/`; portable crates may gain
   OS-neutral hooks only.
3. **`PlatformDecoders` is the natural seam.** It is defined in `rtspcam-pipeline`
   (`src/decode/mod.rs`) and re-exported by `rtspcam-platform`. `rtspcam_platform::install()`
   puts the Windows implementation (`MfDecoders`, an empty struct today) into a private
   `OnceLock`; only `create_decoder` reaches it. It is where VA-API (Linux) and VideoToolbox
   (macOS) would plug in later. Hardware decoding behind this trait, handing back ordinary CPU
   `Frame`s, changes nothing outside the platform crate except a few OS-neutral additions in
   `decode/mod.rs` (8.1a).
4. **Scaling happens late and per consumer**, after crop/rotate/overlay, on the full-resolution
   frame. With a 4K camera feeding a 1080p camera, every portable stage works on 4K pixels.
   Reducing the frame size early is likely worth more than any single faster stage.
5. **Portable CPU wins help every OS.** A faster scaler or converter in `rtspcam-pipeline`
   helps Linux and macOS too, where no hardware decoder exists yet.
6. **GPU-less machines must keep working.** VMs and some servers have no usable D3D11 video
   device ([10 §4](10-progress-cross-platform.md#4-not-verified) item 6). Every GPU step needs
   the current software path as a fallback. GitHub's `windows-latest` runners are such
   machines: CI never runs the hardware path.
7. **Frame Server runs as LocalService in another session.** Sharing GPU textures with it
   means cross-process shared handles with a DACL, plus a D3D device inside the DLL. That is the
   riskiest part of the original plan, and in the process where a crash hurts most
   ([01 §6](01-plan.md#6-risks-and-mitigations)).
8. **A running stream never gets a new decoder.** `decode_loop` (`rtspcam-pipeline/src/pipeline.rs`)
   creates the decoder at the first key frame of a session and drops it only on
   `DecodeMsg::Start`, i.e. a new RTSP session. A decode error only makes it wait for the next
   key frame with the **same** decoder, and errors don't cause a reconnect. A broken decoder
   (lost GPU) would fail at every key frame until the 5 s stall timeout reconnects the whole
   stream; a settings change would not reach running streams at all. This needs a small
   portable change (P8-11).
9. **The engine doesn't know what consumers ask for.** `CameraSource::client_connected(format)`
   logs the format and only counts the client (`add_clients`); previews are only counted too.
   8.2 needs the sizes kept.

## 3. Decisions

| # | Decision | Why |
|---|---|---|
| P8-1 | **Measure before optimizing.** Step 8.0 comes first; later steps go ahead only if the numbers say so. | No per-stage CPU data exists (§1). |
| P8-2 | **Hardware decoding hands back CPU NV12** (decode on GPU, copy back). No GPU types leave `rtspcam-platform`. | Keeps the shared frame contract (§2.1–2.3). |
| P8-3 | **Keep the synchronous Microsoft decoder MFTs and give them a D3D11 device manager** (`MF_SA_D3D11_AWARE` → `MFT_MESSAGE_SET_D3D_MANAGER`), instead of enumerating vendor hardware MFTs (`MFT_ENUM_FLAG_HARDWARE`, which are asynchronous). | Same MFTs, same `ProcessInput`/`ProcessOutput` loop and lessons ([04 §3](04-session-2026-10-09.md#3-lessons-learned-the-non-obvious-parts)); the async event model is a rewrite. |
| P8-4 | **Software fallback is automatic, at creation and while decoding.** If the D3D11 device, the device manager or the MFT's D3D mode fails, the decoder logs it once and uses today's path. A D3D-mode decoder that fails before its first picture is replaced by a software one for that stream (sticky until the stream's next session). The MFT may also fall back on its own and return memory samples; the copy-back handles both kinds per sample. The decoder name says what actually runs, e.g. `Media Foundation (Microsoft H264 Video Decoder MFT, D3D11)`, and is decided after the first picture. | GPU-less VMs (§2.6), driver gaps for some profiles/sizes; the user sees what is used. |
| P8-5 | **An optional output-size limit on `Decoder`** (portable, default no-op) lets the engine ask for frames no larger than what consumers need. The Windows decoder meets it on the GPU before the copy-back. | Shrinks every later stage and the copy-back (§2.4). |
| P8-6 | **GPU frames into the virtual camera are deferred** (8.4 below), not dropped. Only started if 8.0–8.3 miss the target. | Cost and risk (§2.1, §2.7). |
| P8-7 | **The target stays "under 3% CPU per 1080p stream on a mid-range machine"**, measured as process CPU of `rtspcam.exe` plus the Frame Server share, one consumer per camera. | Same goal as 01; now defined so it can be checked. |
| P8-8 | **MJPEG stays software.** The Microsoft MJPEG decoder has no D3D11 mode. | Not worth a separate path; MJPEG cameras are rare. |
| P8-9 | **A visible "Use hardware decoding" checkbox in Settings, on by default when available**, showing the device it will use (e.g. "NVIDIA GeForce RTX 3060 — H.264, H.265"). Disabled, with the reason, when no hardware decoder exists. Details in 8.1a. | Lets users rule the GPU out when troubleshooting, and shows which GPU does the work on machines with two. |
| P8-10 | **Hardware decoding uses the default DXGI adapter** (the one Windows' per-app graphics preference picks), and exactly that adapter is shown. No device picker for now. | One adapter keeps the shared device simple; the Windows setting already lets users choose. A picker can come later. |
| P8-11 | **The decode loop can replace a decoder without a reconnect** (portable, `pipeline.rs`). Two triggers: a new `ErrorKind::DecoderLost` returned by `decode` (device removed, D3D-mode failure before the first picture), and a decoder generation counter in `decode/mod.rs` that `set_use_hardware` increments. In both cases `decode_loop` drops the decoder and creates a new one at the next key frame; the RTSP session keeps running. | §2.8: without it, device-lost recovery waits for the stall timeout and the checkbox doesn't reach running streams. Switching at a key frame shows no placeholder. |
| P8-12 | **Hardware decoding is off in a process until someone turns it on.** The app/engine calls `set_use_hardware(settings.hardware_decoding)`; tests and the CLI stay software unless they ask. | Deterministic tests; the same binaries measure both paths. |

## 4. Steps

### 8.0 Measure (portable, small)

- Add timing per stage: decode, copy-back (later), transform/overlay, scale, pixel-format
  conversion, pipe write. Use `tracing` spans or counters added to the existing per-second
  stream stats (`StreamStats`), so `rtspcam` CLI runs print them next to bitrate and latency.
- A benchmark run with the Docker test server: 1, 4 and 8 streams at 720p, 1080p and (if the
  test server can produce it) 4K, H.264 and H.265, each read by one consumer. Consumers:
  `vcam` reader on Windows; on Linux a real v4l2loopback device through the `Pusher`
  (phase L, [13](13-progress-phase-l.md)); elsewhere a test `FrameSource` reader. Record
  process CPU and the per-stage numbers in a results table in this document.
- Also measure two costs found in a code review (`documentation/manual/02-enhancement-report.md`
  §2.3–2.4): the per-frame `Vec` allocation in the DLL's `feed.rs` (inside Frame Server), and
  two consumers of one camera taking turns on the single `Scaler` lock in `source.rs` (its plan
  is rebuilt on every switch; non-NV12 formats allocate an intermediate `Frame` per call).
- `process_memory()` works on Windows and Linux and is `None` on macOS. Add a process
  CPU-time reading next to it (all OSes) so the same numbers come from Linux runs.
- CLI: the `--decoder` option (`auto`, `platform`/`mf`, `openh264`) gets a way to choose the
  hardware path, e.g. `--hardware on|off` (default off, P8-12), so 8.1 can be compared with
  this table using the same binary.

**Exit:** a table showing which stage costs what. It decides whether 8.1, 8.2 and 8.3 are all
needed and in which order.

### 8.1 D3D11 hardware decoding on Windows (`platform/src/windows/`)

- `rtspcam-platform/Cargo.toml`: add the `windows` features `Win32_Graphics_Direct3D`,
  `Win32_Graphics_Direct3D11`, `Win32_Graphics_Dxgi` and `Win32_Graphics_Dxgi_Common`.
- `MfDecoders` gains state: the cached probe result (8.1a), the on/off flag (an atomic), and
  the shared device and device manager. The trait is `Send + Sync`; if the `windows` crate
  doesn't mark the D3D/MF interfaces as such, wrap them in a type with an `unsafe impl` whose
  safety comment rests on multithread protection being on and `IMFDXGIDeviceManager` being
  free-threaded.
- One D3D11 device for all decoders (`D3D11_CREATE_DEVICE_VIDEO_SUPPORT`, multithread
  protection on via `ID3D10Multithread::SetMultithreadProtected`), wrapped in an
  `IMFDXGIDeviceManager` (`MFCreateDXGIDeviceManager`). Created by the probe (8.1a); if creation
  fails, remember that and go software for the rest of the run.
- In `MfDecoder::new`, when hardware is on and available: if the MFT's attributes have
  `MF_SA_D3D11_AWARE`, send `MFT_MESSAGE_SET_D3D_MANAGER` right after setting `MF_LOW_LATENCY`
  and before `SetInputType`. The MFT then allocates its own output samples (the code already
  handles `MFT_OUTPUT_STREAM_PROVIDES_SAMPLES`). In D3D mode the decoders offer NV12, already
  first in `OUTPUT_PREFERENCE`.
- Copy-back, in `convert()`:
  - Per sample, check whether its buffer is an `IMFDXGIBuffer`. If not (the MFT fell back to
    software for this stream on its own), keep today's path; the name then must not say D3D11.
  - DXGI buffers hold a texture-array slice. Simplest first version: `IMF2DBuffer::Lock2D`,
    which does the staging copy itself and returns the **row pitch**. `picture_to_frame` takes
    its stride from `MF_MT_DEFAULT_STRIDE` or derives it from the buffer length today; give it
    the pitch from `Lock2D` instead (the pitch is usually larger than the width, and the
    coded height can be 1088 for 1080p). Avoid `ConvertToContiguousBuffer` + `Lock` on DXGI
    buffers: it repacks the picture, an extra copy.
  - Switch to our own reused `D3D11_USAGE_STAGING` NV12 texture (`CopySubresourceRegion`,
    `Map`) if 8.0 shows `Lock2D` is slow.
  - Release each output sample right after the copy; D3D-mode MFTs have a small sample pool.
- Name: `Media Foundation (<friendly name>, D3D11)` once the first picture came from a DXGI
  buffer; until then, and on the software path, today's name. Send `DecodeEvent::Ready` again
  (or a rename event) when the name changes after the first picture, so the stream details
  show the right one.
- Fallback while decoding (P8-4): a D3D-mode decoder whose `ProcessInput`/`ProcessOutput`
  fails before its first picture returns `ErrorKind::DecoderLost`; the next decoder for that
  stream is created in software (P8-11).
- Recheck the lessons from [04 §3](04-session-2026-10-09.md#3-lessons-learned-the-non-obvious-parts):
  output-buffer reset only applies to samples we allocate; the HEVC output type without
  `MF_MT_FRAME_SIZE`; the H.265 CRA workaround (in `source.rs`, unaffected).
- Device lost (driver update, GPU reset, `DXGI_ERROR_DEVICE_REMOVED`): drop the shared device
  and return `ErrorKind::DecoderLost`. `decode_loop` makes a new decoder at the next key frame
  (P8-11), which re-runs the probe for a new device. If that fails, software.
- The shared device is created on the adapter found by the probe in 8.1a, never on a different
  one, so what Settings shows is what decodes.
- Portable part (`rtspcam-pipeline`, P8-11): `ErrorKind::DecoderLost`, the generation counter
  in `decode/mod.rs`, and in `decode_loop`: drop the decoder on `DecoderLost` or when the
  generation changed, and create a new one at the next key frame. Test with a fake platform
  decoder that fails once.
- Known gap, unchanged by this step: 10-bit H.265 (Main10) comes out as P010, which
  `OUTPUT_PREFERENCE` doesn't accept, so such streams fail on both paths. The probe reports
  only the 8-bit Main profile.

#### 8.1a Setting: "Use hardware decoding" (P8-9, P8-10)

**Config** (`rtspcam-core`, `AppSettings`): `hardware_decoding: bool`, default `true`, meaning
"use hardware decoding when it is available". `AppSettings` has `#[serde(default)]` at struct
level, so old files without the field get `true` from the `Default` impl (set it there); no
migration needed. The stored value is never changed because hardware is missing, so moving the
config to a machine with a GPU turns it on there.

**Probe** (portable seam, defined in `rtspcam-pipeline/src/decode/mod.rs` next to
`PlatformDecoders`, re-exported by `rtspcam-platform`):

```rust
pub enum HardwareDecoding {
    /// Still probing (it runs on a background thread at startup).
    Checking,
    /// A device that can decode; `codecs` are the ones it accepts.
    Available { device: String, codecs: Vec<VideoCodec> },
    /// Why not, shown under the disabled checkbox.
    Unavailable(String),
}

pub trait PlatformDecoders {
    // ... existing methods ...
    /// What hardware decoding this computer has. Probed once, then cached.
    fn hardware(&self) -> HardwareDecoding { HardwareDecoding::Unavailable("Not available on this system yet".into()) }
    /// Turns hardware decoding on or off for decoders created from now on.
    fn set_use_hardware(&self, _on: bool) {}
}

/// Free functions for the engine, app and CLI, since the installed decoders are private.
pub fn hardware_decoding() -> HardwareDecoding;   // Unavailable when none are installed
pub fn set_use_hardware(on: bool);                // also bumps the generation (P8-11)
```

Windows implementation:
- Take the default adapter (`IDXGIFactory1::EnumAdapters1(0)`). If it is a software adapter
  (`DXGI_ADAPTER_FLAG_SOFTWARE`, e.g. "Microsoft Basic Render Driver" on VMs and CI runners) →
  `Unavailable("No graphics card with video decoding found")`.
- Create the D3D11 device with video support on it; failure → `Unavailable` with the reason.
- Ask `ID3D11VideoDevice` for its decoder profiles: `D3D11_DECODER_PROFILE_H264_VLD_NOFGT` →
  H.264, `D3D11_DECODER_PROFILE_HEVC_VLD_MAIN` → H.265. No profiles at all → `Unavailable`.
  H.265 still needs the HEVC extension for the MFT; its existing hint stays.
- `device` is `DXGI_ADAPTER_DESC1::Description`, trimmed.
- The probe starts from `install()` on a background thread (device creation can take a few
  hundred ms), is logged (`hardware decoding: NVIDIA GeForce RTX 3060 (H.264, H.265)`), and the
  device it created becomes the shared device of 8.1, so it is not created twice. A decoder
  created while the probe is still running waits for it (bounded, e.g. 2 s) or goes software.

Linux and macOS use the default methods until VA-API / VideoToolbox exist (§5): the checkbox
shows, disabled, with "Not available on this system yet".

**UI** (Settings dialog, `rtspcam-app/src/ui/settings_dialog.rs` and the `SettingsDialog`
global in Slint):
- Checkbox **Use hardware decoding**, with a line of text under it:
  - available, on: `Device: NVIDIA GeForce RTX 3060 (H.264, H.265)`
  - available, off: the same text, greyed
  - unavailable: checkbox disabled and unchecked, text is the reason
  - probe still running (`Checking`): checkbox disabled, `Checking…`; filled in when the
    probe finishes
- The stored value is shown as is when available; when unavailable the box shows unchecked but
  `apply()` keeps the stored value (it copies `current` and only overwrites the fields the
  sheet can change), so saving does not overwrite the stored `true`.

**Applying a change:** `CameraManager::apply(config)` already receives the whole `Config`
(from the settings sheet's save and from the file watcher, also in headless mode). When
`settings.hardware_decoding` differs from the last value, the engine calls
`set_use_hardware`; it also calls it once at startup. The generation bump makes every running
stream switch decoder at its next key frame (P8-11), without a reconnect or placeholder;
streams that aren't running pick it up when they start. The per-stream decoder name (with or
without `, D3D11`) shows the result in the stream details.

**Exit:** with a GPU, the log names the D3D11 decoder, Settings shows the same adapter, and CPU
drops compared with the 8.0 table. Unchecking the box switches running streams to the software
decoder without restarting the app or reconnecting. On a GPU-less VM, the checkbox is disabled
with a reason and the software decoder runs. Existing decoder tests pass on both paths:
software in CI (P8-12; CI has no GPU), and a hardware variant of
`rtspcam-platform/tests/windows_decode.rs` that turns hardware on and skips with a message when
`hardware_decoding()` is not `Available` — run by a person on a machine with a GPU.

### 8.2 Smaller frames earlier (portable hook, Windows implementation)

- Add to the `Decoder` trait: `fn limit_size(&mut self, max: Option<(u32, u32)>) {}` (default
  no-op, so OpenH264 and future decoders are unaffected). The decoder lives on the decode
  thread, so the limit reaches it through a new `DecodeMsg` (or a shared value read before each
  decode), set by the engine through `Pipeline`.
- Record what consumers ask for (§2.9): keep each consumer's `VideoFormat` from
  `client_connected` in `CameraShared` (remove on disconnect), and the preview's display size
  in `add_previews`. On Linux the v4l2loopback device's format is fixed when the camera is
  created, so the size is known up front.
- The engine works out the limit per stream: the largest size any current consumer (and the
  preview) asks for, mapped back through crop and rotation so no source detail that would be
  shown is lost. With no consumer, or when the source is already small enough, no limit.
  The limit changes only when consumers change, not per frame.
- Windows: when a limit is set and smaller than the decoded size, scale on the GPU on the same
  D3D11 device, between the decoder and the copy-back. Two ways; pick the simpler one when
  building: `ID3D11VideoContext::VideoProcessorBlt` directly on the decoder's texture into a
  smaller NV12 texture (no second MFT and no second type negotiation), or the Video Processor
  MFT (`CLSID_VideoProcessorMFT`). The copy-back then moves the smaller frame. Software
  decoding ignores the limit (the CPU scaler does the work as today).
- The per-consumer `Scaler` stays: it still fits the frame to the exact output size and
  letterbox/crop mode. When the frame already has that size, its existing row-copy path
  applies.
- Related, not part of this step: using the camera's sub stream for small consumers and the
  preview (enhancement report, ONVIF already lists both streams) would cut decode work too.
  It needs its own plan for switching streams during a call.

**Exit:** a 4K source feeding a 1080p camera shows 1080p-sized frames after the decoder, and
CPU drops accordingly in the 8.0 benchmark.

### 8.3 Faster portable CPU stages (only if 8.0 says so)

- SIMD for the scaler and the NV12 → BGRA/YUYV/I420 conversions in `rtspcam-pipeline/src/scale.rs`
  (via `std::arch` with runtime detection, or a vetted crate), keeping the current scalar code
  as reference and as fallback. Compare outputs in tests.
- Cache the scaled result per (frame, format) so two consumers of the same camera don't scale
  twice, and so they no longer take turns on one `Scaler` (whose plan is rebuilt on every
  switch). Scale into reused buffers instead of a new intermediate `Frame` per call.
- Reuse buffers in the DLL's `feed.rs` (a small pool, or `MFCreateVideoSampleAllocatorEx`)
  if 8.0 shows the allocation churn inside Frame Server matters.
- Helps Linux and macOS too, where decoding stays on the CPU.

### 8.4 GPU frames into the virtual camera (deferred)

Only if the target is still missed after 8.1–8.3. What it would take, for the record:

- A second `Frame` representation (GPU texture handle) behind a portable opaque type, with a
  CPU fallback for the preview, the overlay, `Pusher` backends and older DLLs.
- A protocol version 2 message carrying a shared NT handle (`IDXGIResource1::CreateSharedHandle`)
  that Frame Server's LocalService account may open (DACL as on the pipe), plus keyed-mutex
  or fence synchronisation.
- The DLL opening the handle on the D3D manager Frame Server gives it and handing out DXGI
  samples, with CPU samples for consumers that provide no D3D manager.
- Overlay, crop/rotate and scaling done on the GPU (Video Processor or a shader).

This is a large, Windows-only change in the DLL, the riskiest process (§2.7). It also does
not apply to Linux, and macOS would need its own IOSurface version.

## 5. Linux and macOS

Not part of Phase 8. The plan leaves room for them:

- VA-API (Linux) and VideoToolbox (macOS) decoders go behind `PlatformDecoders` the same way
  as 8.1, returning CPU NV12, and may implement `limit_size` (8.2). They implement `hardware()`
  and `set_use_hardware()` (8.1a), so the same checkbox and device line work there, and they
  get decoder replacement (P8-11) for free.
- 8.0 measurements and 8.3 apply to every OS as they are. Linux can measure with real
  v4l2loopback cameras now that phase L is done.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Driver bugs in D3D11 decoding (corrupt frames, hangs) on some GPUs | Automatic fallback on errors (P8-4, P8-11); device-lost handling; the "Use hardware decoding" checkbox lets users turn it off (8.1a). |
| The MFT silently decodes in software despite the D3D manager (unsupported profile or size) | Copy-back checks each sample's buffer type; the name only says D3D11 when it is true (8.1). |
| The shown device is not the one decoding (hybrid laptops with two GPUs) | The decoder's device is the one the probe created and named (P8-10, 8.1a). |
| Copy-back costs more than expected (large frames, integrated GPUs) | 8.2 shrinks frames first; own staging texture instead of `Lock2D`. |
| Shared D3D11 device becomes a contention point with 8 streams | Multithread protection is on; if 8.0 shows contention, one device per few decoders. |
| `limit_size` hides detail the user wants (crop on a 4K source) | Limit computed through crop and rotation; no limit when unsure. |
| Behaviour differs between hardware and software paths (colour, odd sizes, apertures) | Same `read_format`/aperture code on both paths; tests force both. |
| CI never runs the hardware path (no GPU on runners) | Hardware tests skip without a device; a person runs them on a GPU machine before release (8.1a exit). |

## 7. The rest of Phase 8, in short

Unchanged in goal, adjusted for the cross-platform code:

- **Shared-memory IPC:** only if 8.0 shows the pipe as a bottleneck. It would be another
  `FrameTransport`/`FrameListener` implementation, not a protocol change.
- **Soak tests:** the headless engine can soak on Linux too (for the ~9 MB/h memory drift,
  [03 §4.2](03-progress-phases-2-3.md#42-phase-2-exit-criteria)); Frame Server restarts, user
  switching and sleep/resume stay Windows scenarios.
- **Compatibility matrix:** organised by OS; Windows and Linux (phase L, see
  [13](13-progress-phase-l.md)) filled in now, macOS after phase M.
