## 3. Lessons learned (the non-obvious parts)

These cost the most time. Keep them in mind when touching the related code.

**Media Foundation**
- **Reset the output buffer before every `ProcessOutput`.** When the decoder's output sample is
  reused, `GetBufferByIndex(0).SetCurrentLength(0)` must be called first. Otherwise the H.264
  MFT fails every picture after the first with "CopyDecodedFrame failed", and the HEVC MFT
  reports "attribute not found". This was first blamed on setting the input frame size, which
  turned out to be harmless and is set again for all codecs.
- The HEVC MFT can offer output types without `MF_MT_FRAME_SIZE`; treat it as unknown (0) until
  the stream-change event.
- `MFCreatePresentationDescriptor` with no stream descriptors returns `E_POINTER`. Create the
  stream (and its descriptor) first, then the source, then link them with `set_source`.
- Synchronous `IMFSourceReader::ReadSample` needs the stream-flags out-parameter even if you
  ignore it; passing `None` gives `E_POINTER`.
- `MFCreateVirtualCamera` is resolved from `mfsensorgroup.dll` at run time so the exe still runs
  (and explains itself) where it doesn't exist.

**RTSP / retina**
- retina only marks IDR pictures as key frames. Open-GOP H.265 (CRA pictures) therefore never
  got VPS/SPS/PPS and never decoded. `source.rs` detects any IRAP NAL (types 16–23) and
  prepends the parameter sets itself. Worth an upstream issue.
- retina ends the session on one malformed fragment ("FU has start bit unset", seen on H.265
  after a server restart). The normal reconnect handles it (~8 s).
- `FrameFormat::SIMPLE` gives Annex B with parameter sets on key frames, which is what both
  decoders want.

**Test server (mediamtx + ffmpeg in Docker)**
- RFC 2435 needs standard Huffman tables: `-huffman default`. Even then mediamtx rejects
  ffmpeg's RTP/JPEG ("received wrong fragment"), so MJPEG streaming is untested (the decoder is
  tested with `tests/fixtures/split-320x240.jpg`).
- An unknown path gives 400, not 404; the test accepts either classification.
- Docker Desktop doesn't forward RTP over UDP to the host (error 10054); the UDP test is opt-in
  with `RTSPCAM_TEST_UDP=1`.
- ffprobe prints warnings before its CSV output; the probe script reads the last line.

**Build and tooling**
- The DLL's exports go through `exports.def` (`PRIVATE`) passed by `build.rs` with `/DEF`;
  `#[no_mangle]` alone gave LNK4104 for the `Dll*` entry points.
- Clippy's undocumented-unsafe lint is on: every `unsafe` needs a `// SAFETY:` comment.
- PowerShell: don't name variables `$args` or `$Profile` (automatic variables).
- Git Bash rewrites `/tmp`-like arguments to Windows paths; use `MSYS_NO_PATHCONV=1` when
  passing container paths to `docker exec`.

## 4. Results

- Phase 2 exit criteria met: 4 streams at 30 fps, recovery from `docker restart` in 1–2 s
  (H.265 ~8 s), receive-to-decode latency 2–14 ms.
- 1-hour soak, release build: ~108,000 frames per stream, 0 decode errors, 0 packets lost, no
  reconnects. Private memory 108 → 117 MB. **Open question**: fragmentation or a slow leak;
  recheck with the longer Phase 8 soak (or sooner, with a heap profiler, if it grows further).
- Phase 3 verified in-process only: `IMFSourceReader` sees the 12 formats, pacing is a steady
  30 fps, app frames arrive over the pipe, RGB32 format switch works, no leaked objects. The
  built DLL also works through its `DllGetClassObject` export (`vcam test --pattern`).
- `cargo test --workspace`, clippy and `cargo fmt --check` clean. CI has **never run** on
  GitHub; the MF tests may fail on Windows Server runners without the Media Feature Pack.

## 6. How to resume

1. After the install, run the Frame Server checks in order:
   ```powershell
   cargo run -p rtspcam-cli -- vcam status
   cargo run -p rtspcam-cli -- vcam add --name "RTSP Cam Test" --pattern   # keep running
   cargo run -p rtspcam-cli -- vcam list                                    # second terminal
   cargo run -p rtspcam-cli -- vcam read "RTSP Cam Test" --pattern --seconds 10
   ```
2. Read `%ProgramData%\RtspCam\logs\vcam.log`. If the source logged its attribute keys instead
   of resolving the camera id, the `AddProperty` route (S0.2) doesn't work under Frame Server;
   switch to the fallback, a pool of CLSIDs (one registered per camera slot).
3. Check the camera in the Windows Camera app and Discord (needs a person), then Chrome and OBS.
4. S0.6: stop `vcam add` normally and with a hard kill (`Stop-Process -Force`); the camera must
   disappear both times.
5. The Phase 3 exit run: 1 hour in a camera app, plus start/stop/reselect cycles, watching the
   Frame Server process for leaks.
6. Then push and get CI green, and start Phase 4 (camera manager in `rtspcam.exe`; move
   `BusSource` out of the CLI into the app).
