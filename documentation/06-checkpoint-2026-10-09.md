## 2. What works today (seen running, on Windows 11)

- The app opens, lists streams, shows a live preview with codec, size, fps, bitrate and latency
  (screenshot in the README: a real 2304x1296 H.264 camera, 14.9 fps, 7 ms decode latency).
- Add/Edit dialog with validation, pasted URLs and Test connection; Settings; tray icon;
  minimize to tray; single instance; Close/Quit ends the process in about 40 ms.
- Each enabled stream becomes a Windows virtual camera. The status line shows
  `Camera "<name>" is available to apps`.
- Through Frame Server (`vcam add --pattern` + `vcam read`): 30 fps, 12 formats, pattern frames
  received intact.
- A hard kill of the process removes its cameras.

## 3. Decisions made since 03/04

| Topic | Decision |
|---|---|
| Camera identity (S0.2) | The stream id and preferred format are string attributes on the `IMFVirtualCamera`, delivered to the source in its activation attributes. `AddProperty` / `AddRegistryEntry` are refused (`E_ACCESSDENIED`) for current-user cameras; that was the "Access is denied" users saw. The CLSID pool is not needed. |
| Stale cameras | No startup sweep. Session-lifetime cameras vanish with the process, including a hard kill (S0.6). |
| Pipe liveness | Use `WaitNamedPipeW`, never `Path::exists`, which connects and steals a pipe instance. |
| UI toolkit details | winsafe for windows and controls; the `windows` crate for tray, icon and GDI painting (winsafe lacks them). Preview is GDI, not Direct2D. Status is polled by timers. |
| Rust version | `winsafe` needs 1.87, the workspace declares 1.85; the pinned stable toolchain builds it. Raising `rust-version` triggers new MSRV-gated clippy lints in old crates, so it was left. |
| Next document number | `07` is the Phase 6 record; the Phase 0 decision record, if ever written, is `08`. |

  - the memory drift seen in the one-hour Phase 2 soak (~9 MB/h) on a longer run.

## 5. Known problems and rough edges

- **Test connection** fails with `EOF while expecting response to PLAY` if the camera only
  allows one RTSP session and the stream is already playing. Not handled specially.
- **MJPEG streaming** is untested end to end (the test server cannot relay it); H.265 needs the
  Microsoft HEVC extension, and the UI shows the hint.
- `vcam list` no longer shows RTSP Cam stream ids (it read a device property that no longer
  exists).
- Windows reports `0x80070005` when the media source is not registered, so the app shows a
  combined "not installed, or unreadable by Frame Server" message.
- Color range: BT.709/601 are chosen by height; full-range MJPEG is not converted.
- Unit tests for window code do not exist; the UI was checked by running it. A native
  exception in a paint handler exits the process with `0xC000041D` and no log line.
- The release build hides the console, so `--headless` output goes only to the log file.
- Windows 10, audio, RTSPS and HTTP MJPEG are out of scope (plan §5).

## 6. How to resume

```powershell
cargo build -p rtspcam-cli -p rtspcam-vcam
./tools/vcam/install-dev.ps1          # once per DLL change; UAC prompt
cargo run -p rtspcam-app
./tools/test-rtsp/start.ps1 -Detach   # test streams on 127.0.0.1:8554 (Docker)
```

Then, in order:

1. Look at the CI run for the last push and fix whatever it reports.
2. Do the person-only checks in §4, starting with Discord (restart it after adding a camera).
   Record the results in a compatibility table (plan Phase 8) or a new numbered document.
3. Phase 7 is the next blocker for anyone but the developer: an installer that registers the
   DLL under Program Files, removes cameras on uninstall, and checks for Windows 11.
4. Phase 6 is done (see [07](07-progress-phase-6.md), which also lists what still needs a
   person). Phase 8 can follow Phase 7 or come before it.

Addendum: the Add/Edit dialog's start-up code never ran in Phases 4-5 (a winsafe `WindowModal`
gets `WM_CREATE`, not `WM_INITDIALOG`), so the Test connection result was never shown until this
was fixed in Phase 6. See 07, section 3.
